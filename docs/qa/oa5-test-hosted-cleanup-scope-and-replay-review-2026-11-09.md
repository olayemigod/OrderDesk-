## 09/11/2026 — Supabase CLI v3 hosted reset sequencing decision (candidate only)

The current [official Supabase CLI guidance](https://supabase.com/docs/guides/local-development/local-and-hosted-projects) (updated 02/11/2026) and [CLI reset reference](https://supabase.com/docs/reference/cli/supabase-db-reset) establish an important distinction:

- In **v3**, database commands with no remote target default to the **local** stack; an explicitly supplied project reference in the remote target selects a **specific hosted project**, overriding any checkout's linked project or SUPABASE_PROJECT_ID. The CLI displays the resolved Target before mutating.
- A **remote** database reset identifies and drops **user-created database entities** and replays local migration files (and seed files unless explicitly disabled). It does **not** promise a complete wipe of managed Auth, Storage object bytes, Edge Functions, provider callbacks, job configuration, Vercel, deployed clients, externally delivered messages or cluster-level custom PostgreSQL roles. Vault/seed/role side effects must be independently reviewed.
- The v3 hosted-operation confirmation is a **single pre-change prompt, default No**, with an explicit list of target changes. Noninteractive agents/CI cannot answer it; a bypass confirmation flag or shell environment variable would be a **destructive operation**, not evidence review. Do not run it under this PR. The existing Database CI remains pinned to the older v2 CLI; no CLI upgrade or remote invocation is approved here.

**Critical ordering conflict:** a remote reset both retires historic user-created objects **and immediately replays canonical migrations**. Those migrations can recreate public/private foreign keys into Auth before historical Auth-user retirement is complete. This does **not** implement the proposed separate Stage C old-schema retirement → Stage D supported Auth cleanup → Stage E canonical replay order in one step. Historical Supabase-managed Auth users/sessions and legacy Storage also persist across remote database reset. Consequently, **remote reset is not approved as a one-command OA5 cleanup/rebuild** even though its SQL object-retirement semantics are documented.

**Remaining method decision:** the independent operator must either (A) document a supported, recoverable, tested **staged** historical user-created-object retirement and migration ledger handoff permitting separately approved Auth/Storage actions before canonical replay; or (B) prove an alternative **retain-and-quarantine** policy for old managed Auth identities and historic previews that still meets synthetic-only QA and privacy requirements, then choose an exact-target hosted reset+replay path with managed-service residual checks. Neither branch is selected here. Both require the same encrypted Agreement/audit custody, provider freeze, four-job quiescence, protected old Preview evidence, reviewed SQL/permission/extension dependencies, rollback operator and **operation-specific destructive approval**. The agent must not issue SQL drops, migration repair, CLI resets or an all-function deployment to make the history appear clean.

**Source-only recommendation:** first reproduce any candidate cleanup operation's user-object dependency closure and full canonical replay in a **disposable local PostgreSQL/Supabase environment**, capturing independent before/after catalog, Auth FK, RLS/function-grant and migration-ledger evidence. A green local replay alone still does not authorize a remote operation or certify Auth/Storage/Meta/PSP/email/FCM isolation. PR #228 remains draft and the hosted OA5 attestation blocked.
