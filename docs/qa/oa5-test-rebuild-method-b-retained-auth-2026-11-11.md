## Known Supabase CLI v3 behavior and critical limitation

Current Supabase CLI documentation indicates that v3 remote database reset operates against explicitly targeted hosted projects, identifies/drops **user-created database entities**, and replays the source migrations. Remote reset can also run configured seed files unless disabled. It is **not** a complete wipe of managed Auth, Storage physical objects, existing Edge deployments, external integrations, Vercel deployments, secrets or cluster-level roles; exact CLI v3 version, target, reported object list, seed behavior, privileges, and post-state must be reverified by the nominated operator before any mutation. The project CI database replay uses the older local-only v2 CLI and is **not** a hosted CLI v3 acceptance test.

**Critical ordering distinction:** One remote reset combines historical user-created-object retirement **and immediate canonical replay**. Therefore it does not permit an intermediate hard-delete of old Auth accounts between schema retirement and canonical replay, and it is unsuitable for candidate A without a different staged method. Candidate B deliberately **retains** managed Auth but requires positive evidence that old accounts cannot inherit fresh canonical permissions. The remote reset must never be inferred to revoke old JWT access or disable already scheduled cron jobs. The operator must independently establish the exact Test-only object and grant effect, not merely count migrations.

References: [Supabase CLI reset](https://supabase.com/docs/reference/cli/supabase-db-reset), [CLI local/remote workflow](https://supabase.com/docs/guides/local-development/cli-workflows), [Auth users](https://supabase.com/docs/guides/auth/managing-user-data), and [Storage deletion API](https://supabase.com/docs/guides/storage/management/delete-objects).
